# 人才标签冗余表清理说明

## 目标结构

人才标签只保留以下两张活动业务表：

- `tal_tag`：标签字典，字段为 `id/name/category/description/is_builtin/created_at`。
- `tal_talent_tag`：人才标签关联，复合主键为 `talent_id/tag_id`，附带 `source/score`。

旧的 `tal_talent_dict`、`tal_talent_tag_rel` 不再有 ORM、DAO 或服务调用方。
前端 `/talent-dicts` API 路径暂时保留，内部已经直接使用目标表，避免造成接口破坏。

## 数据映射

Revision `e2f6a9c3d701` 在退出旧表前执行以下映射：

| 旧字段 | 新字段 | 规则 |
|---|---|---|
| `tal_talent_dict.name` / `code` | `tal_tag.name` | 优先使用 `name`，为空时使用 `code`；按名称去重 |
| `type=experience` | `category=exp` | 分类标准化 |
| `type=fit` | `category=position` | 分类标准化 |
| `type=strength` | `category=custom` | 分类标准化 |
| 其他已知 `type` | `category` | 保持或映射到对应分类，未知值归入 `custom` |
| `tal_talent_tag_rel.dict_id` | `tal_talent_tag.tag_id` | 通过旧字典 ID 到新标签 ID 的映射转换 |
| `weight` | `score` | 转为浮点置信度 |
| `source` | `source` | 保留；冲突时 `manual` 优先 |

迁移会在修改表结构前拒绝重复标签名、空标签名、无效人才 ID、无效字典 ID
以及无法识别的字段结构，防止静默丢数。

## 删除与回滚策略

为保证 MySQL 和 SQLite 都能无损回滚，旧表迁移完成后改名为 revision 专属隔离备份：

- `_bak_e2f6a9c3d701_tal_talent_dict`
- `_bak_e2f6a9c3d701_tal_talent_tag_rel`

因此旧活动表名已经删除，应用和后续 ORM 建表不会再使用它们。执行 `downgrade -1`
会将隔离表原样改回旧表名。确认经过备份保留期且不再需要数据库级回滚后，可再用独立迁移删除隔离表。

## 执行

当前共享库原有 merge revision `d4e5f6a7b8c9` 的文件已经恢复，执行迁移前不再需要
手工修改 `alembic_version`：

```powershell
$env:PYTHONUTF8 = "1"
alembic current
alembic upgrade head
```

升级前应停止写入，并先备份数据库。当前共享库审计显示两张旧表已经不存在，
因此该库执行 `e2f6a9c3d701` 时清理部分为幂等空操作；其他仍有旧表的环境会执行数据合并和隔离。
