## 三、目标与验收总则

### 3.1 三日目标
全量功能覆盖 + 五大 Agent 可演示 + 至少一条多 Agent 协同闭环跑通 + 双端可登录可用。

### 3.2 验收口径
> **功能必须实现（硬），Agent 可以不够聪明（软）。**

| 维度 | 硬验收（必须达标） | 软验收（不卡交付） |
|------|------------------|------------------|
| Agent 存在性 | 五大 Agent + LangGraph 多 Agent 协同图全部落地 | 无 |
| 功能实现 | 每个模块的 AI 功能有完整可用实现 | 无 |
| 智能程度 | —— | 不做及格线：效果、准确率、精度均可演示即可 |
| 协同链路 | 至少一条多 Agent 协同闭环可跑通 | 协同时长、状态机健壮性（基础版即可） |

## 七、框架交付物 + 扩展接入指南

> 本期真正的交付物不止功能点，更是一个**可直接扩展的全栈分层框架**。

### 7.1 前端 - 后来者如何加一个页面
1. **后端已就位的**：Axios 封装带 token、响应拦截、路由守卫、Pinia store 模板、统一样式
2. 新增业务页面只需：在 `views/<module>/` 建页面 → 在 `router` 加路由并挂到对应菜单 code → 调后端接口
3. 权限菜单：菜单/权限码已由 A06 管理，新页面在"菜单管理"挂一个 code 即自动按角色可见
4. 加接口自动带鉴权：后端路由统一走 JWT 依赖，无需重写

### 7.2 后端 - 后来者如何加一个模块
1. `models/<module>.py` 建表 → alembic 迁移
2. `schemas/<module>.py` Pydantic 校验 → `dao/` 数据访问 → `services/` 业务 → `routers/` 挂路由
3. 接口签名提交 `/docs`，前端即可并行；**分层依赖 router→service→dao→model 单向**
4. 统一响应/异常/分页组件已由脚手架铺好，直接复用

### 7.3 横切能力（本期已固化，业务直接调用）

| 能力 | 位置 | 业务如何接入 |
|------|------|-------------|
| 鉴权/RBAC | JWT 依赖 + 角色权限码 | 接口加 `Depends(require_permission("code"))` |
| 操作留痕 | 全局中间件 | 增删改查自动记录，业务零侵入 |
| 消息推送 | msg service | 业务写一行 `notify(type, users, payload)` 即推送 |
| 审计/脱敏 | audit + 序列化脱敏 | 敏感字段加脱敏注解即自动脱敏 |
| 数据字典 | dict service | 业务枚举项走字典，改配置不改代码 |
| Agent | ai/agents/<name>.py | 新 Agent 按 `输入→LLM→JSON→落库` 模式开发 |

### 7.4 Agent 开发规范
- 每个 Agent 独立文件 `ai/agents/<name>_agent.py`，实现 `async def run(input_data) → result_dict`
- 统一用 LangChain + Ollama，输出严格 JSON Schema 校验
- Agent 之间通过 LangGraph StateGraph 编排协同，不直接互相调用
- 验收口径：功能可用（硬）+ 效果可优化（软）

## 十一、Git 协作规范

```
main（稳定，仅发版）
 └─ develop（每日集成线）
     ├─ feature/B-talent-crud
     ├─ feature/agent1-resume
     ├─ feature/C-assessment
     └─ ...
流程：feature/xxx → develop（每日15:00合并）→ 演示前一晚打 beta
命名：feature/<模块>-<短名>；提交：feat(scope): 描述
```

- 每人独立模块开发，避免抢文件
- 每日集成一次、冲突及时解、禁直提 main
- 改动接口必须通知调用方（禁止静默改字段）
- 公共代码（auth/middleware/config）由 P1 统一管理

全程：横切能力（鉴权/留痕/消息/字典）由 P1/脚手架提供
